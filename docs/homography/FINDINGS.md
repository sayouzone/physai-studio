# 근본 원인 확정 및 수정 (원본 + summary.json 기반)

원본 이미지와 `summary.json` 덕분에 이번엔 추측 없이 원인을 특정했습니다.
**앞선 세 차례 제 진단(평면 높이, 시임 위치, 프레임 정렬)은 모두 증상이었고,
진짜 원인은 SfM 단계에 있었습니다.**

## 1. 측정으로 후보를 하나씩 제거

| 후보 | 실측 | 판정 |
|---|---|---|
| 초점거리 혼입 (`_Z` 줌 카메라) | 전 프레임 `FocalLengthIn35mmFilm=47`, f_px=6768 동일 | 아님 |
| 렌즈 왜곡 (DewarpData 없음) | 직선 50개 plumb-line 적합 → k1≈−0.017, 모서리 **0.08 m** | 아님 (기여 8%) |
| 반복 격자로 매칭 실패 | 실제 패널 텍스처 겹침쌍에서 ratio 0.75 → **inlier 2469개** | 아님 |
| 평면 장면에서 F-행렬 퇴화 | F 2472 vs H 2469 — 둘 다 정상 | 아님 |
| RTK 오차 | σ≈1 cm → 지상 0.01 m | 아님 |
| **자세오차** | 1 m 를 만들려면 **1.3°** 필요 | **이것** |

## 2. 자세가 왜 안 잡히나 — 순환 실패

`summary.json` (380장):

* 평면 적합 inlier **147개 / 380장 = 이미지당 0.4개.** 고중복 380장이면
  수천~수만 개가 나와야 합니다. **BA 점군이 사실상 비어 있습니다.**
* 재투영 RMSE 0.58 px 는 관측이 극소수라 낮게 나온 값이지 자세가 잘 풀렸다는
  뜻이 아닙니다.
* 모자이크 정렬 보정 60/380장, **최대 0.999 m — 상한 1.0 m 에 정확히 잘림.**

원인은 `pipeline.py` 의 삼각측량 게이트입니다:

```
triangulate_tracks(..., max_reproj_err_px=3.0)     f_px = 6768
  → 초기 자세오차가 3/6768 rad = 0.025° 를 넘으면 그 점은 버려진다
```

짐벌 보고값은 0.1° 단위이고 광축 절대 정확도는 그보다 나쁩니다. 실제 필요한
보정량 1.3° 는 **154 px** 이므로 3 px 게이트가 전부 버립니다.

```
삼각측량이 점을 버림 → BA 가 자세를 못 고침 → 다음에도 같은 점이 버려짐
```

**순환 실패**입니다. 게이트를 초기 자세 불확실성에 맞춰 열어 주지 않으면
BA 는 영원히 시작하지 못합니다.

## 3. 수정 — 2단계 삼각측량 + BA

느슨한 게이트로 1차 BA(자세를 대략 맞춤) → 그 자세로 다시 삼각측량하되 이번엔
조인 게이트 → 2차 BA(정밀화). 표준 incremental SfM 관행입니다.

합성 검증 (카메라 30, 점 600, **실측과 같은 1.3° 자세오차 주입**):

| | 생존 점 | BA 후 자세오차 | 지상 환산 |
|---|---|---|---|
| 기존 (게이트 3 px 단일) | **0개 (0.0%)** → BA 생략 | 1.300° | **1.02 m** |
| 신규 (708 px → 3 px) | 588개 (98.0%) | **0.011°** | **0.009 m** |

기존 방식은 점이 하나도 살아남지 못해 BA가 아예 실행되지 않습니다. 관측된
증상(inlier 147개, 정렬 보정 1 m 포화)과 정확히 일치합니다.

## 4. 함께 넣은 것

* `homography/align.py` — 겹침 쌍 SIFT 대응으로 상대 이동량을 재고 **전역
  최소제곱 네트워크**로 프레임 오프셋을 푼다. 기존 greedy 정렬(캔버스 1:1,
  60/380장만 보정)의 대체. 부호 규약은 통제 실험으로 확정했습니다
  (주입 +0.6 m → 측정 −0.595 m).
* `homography/guided_match.py` — RTK 예측 반경으로 매칭을 좁히는 경로.
  이번 데이터에서는 일반 매칭도 충분했지만, 중복이 낮거나 셀 격자가 더
  조밀한 현장을 위해 남겨 둡니다.
* `ortho.py` 의 `align_max_m` 기본값 1.0 → 1.2 (행 주기 2.72 m 의 절반 미만).

## 5. 실행

```bash
python scripts/homography_pipeline.py \
    --image-dir .../RGB --output-dir .../output \
    --attitude-deg 1.5
```

**로그에서 꼭 확인할 줄:**

```
[stage] triangulation 1차(느슨) (게이트 ... px): 점 N개, 관측 M개
  누적 자세 변화: 중앙값 X.XXX°, 최대 ...  (지상 환산 중앙값 ... m)
[stage] triangulation 2차(정밀) (게이트 3 px): 점 N개, 관측 M개
```

* 1차 점 개수가 **이미지당 5개 미만**이면 경고가 뜹니다 → `--attitude-deg` 를
  올리거나 매칭 품질을 보세요.
* 누적 자세 변화 중앙값이 1° 근처로 나오면 이번 진단이 맞은 것입니다.
* 2차 점 개수가 1차와 비슷해야 정상입니다. 크게 줄면 BA가 수렴하지 않은 것.

## 6. 남은 한계

* 합성 검증만 했습니다. 실데이터 380장에서 1차 점 개수가 실제로 수천 개가
  나오는지 확인이 필요합니다.
* 렌즈 왜곡 k1≈−0.017 은 아직 적용하지 않았습니다 (기여 0.08 m). BA가 자세를
  잡은 뒤에도 프레임 가장자리에 8 cm 급 잔차가 남으면 그때 넣는 것이 순서입니다.
* 자세가 잡히면 모자이크 정렬은 거의 트리거되지 않아야 합니다. 여전히 0.5 m
  이상 보정이 다수 나오면 BA가 아직 부족하다는 신호입니다.

# 후속: `ValueError: 612 Mpx 가 상한 초과` 수정

## 원인

상한 400 Mpx 는 알고리즘의 한계가 아니라 **구현 제약**이었습니다.
`mosaic_frames` 가 캔버스 전체를 메모리에 올렸기 때문입니다.

| 출력 | 캔버스(uint8) | 점수맵(float32) | 합계 |
|---|---|---|---|
| 24859×15839 = 394 Mpx (이전, 성공) | 1.18 GB | 1.57 GB | 2.76 GB |
| 30913×19785 = 612 Mpx (이번, 실패) | 1.83 GB | 2.45 GB | 4.28 GB |

## 수정: 타일 스트리밍

출력을 가로 띠로 나눠 한 번에 하나씩만 메모리에 두고 GeoTIFF 에 곧바로
써 넣습니다. 메모리가 출력 크기와 무관해지므로 상한이 필요 없어집니다
(안전장치로 8 Gpx 만 남겼습니다 — 자세가 발산했을 때 잡기 위한 용도).

타일 방식에는 함정이 두 개 있었고, 둘 다 실측으로 잡았습니다.

**1. 타일 경계 밝기 단차.** 노출 이득과 시임 판정이 타일마다 새로 계산되면
경계에서 선택이 달라집니다. 실측에서 경계의 행간 밝기 변화가 주변의 8~40배로
튀었습니다.

**2. 타일 분할에 따라 결과가 달라짐.** 시임 비용의 정규화 상수와 블러가
타일별 창에 의존해, 같은 입력인데 타일 수만 바꿔도 픽셀의 **11.7~13.9%** 가
달라졌습니다.

해결: 시임 결정은 어차피 `seam_cost_blur_m`(1.5 m)로 블러한 저주파 정보이므로,
**저해상도 사전 패스에서 전역 라벨맵(픽셀별 승자 프레임)과 노출 이득을 한 번만
확정**하고 본 패스는 적용만 합니다. 라벨 조회는 전역 좌표 아핀 역매핑으로 하여
타일 오프셋의 영향을 없앴습니다.

검증 (12장, 61 Mpx 출력):

| | 결과 |
|---|---|
| 타일 5개 vs 1개 결과 차이 | **최대차 0, 불일치 0.0000%** |
| 타일 경계 밝기 변화 | 0.163 (전체 중앙값 0.042) — 단차 없음 |

## 범위가 커진 것 자체에 대해

폭 1.244배, 높이 1.249배로 두 축이 비슷하게 늘었습니다. 프레임 하나가 튄
것이라기보다 BA 가 카메라를 실제로 움직였거나 데이터셋이 커진 결과로 보입니다.
구분할 수 있도록 `_robust_bounds` 가 카메라 위치 중앙값에서 크게 벗어난
프레임을 찾아 경고하고 `stats["outlier_frames"]` 에 남깁니다. **경고가 뜨면
2단계 BA 로그의 "누적 자세 변화 최대" 값을 함께 보세요** — 특정 프레임만
과도하게 움직였다면 그 프레임의 RTK/자세를 확인해야 합니다.

## 새 옵션

```bash
python scripts/homography_pipeline.py ... --tile-memory 256
```

메모리가 넉넉하면 늘려서 타일 수를 줄일 수 있습니다 (결과는 동일함이
검증됐습니다). `--gsd` 를 키워 출력을 줄일 필요는 이제 없습니다.

# 후속: 바깥 영역 품질 저하

## 측정

`mosaic_4.tif` 를 194개 블록으로 나눠 국소 어긋남을 재면 **방사형 추세**가
뚜렷합니다.

| 중심으로부터 | 블록 수 | 국소 어긋남 중앙값 | 상관 |
|---|---|---|---|
| 안쪽 1/3 | 81 | **0.061 m** | 0.98 |
| 중간 | 79 | 0.122 m | 0.96 |
| 바깥 1/3 | 34 | **0.321 m** | 0.74 |

중앙은 6 cm 로 좋고 바깥이 5배 나쁩니다. 원인은 두 가지이며 **둘 다 바깥에서만
커집니다.**

**(1) 가장자리는 프레임 최외곽을 쓸 수밖에 없다.** 내부는 중복이 12.8배라
`select` 가 알아서 연직 근처만 고릅니다. 그러나 모자이크 가장자리는 그 지점을
찍은 프레임이 하나뿐이라 선택의 여지 없이 프레임 최외곽(H20T 기준 k=0.479,
25.6°)이 쓰입니다. 거기서 기복변위 `Δh·k` 가 최대입니다.

| 층 | Δh | k=0.479(최외곽) | k=0.35 | k=0.25 |
|---|---|---|---|---|
| 지면(111.8) | 1.87 m | **0.895 m** | 0.654 m | 0.468 m |
| 패널 상면(114.2) | 0.53 m | 0.254 m | 0.185 m | 0.133 m |

**(2) 가장자리 프레임은 BA 제약이 약하다.** 이웃이 적어 tie point 가 적은데,
RTK prior 가중치는 전 프레임 동일했습니다. 영상 제약이 약한 프레임일수록
소수의 관측에 끌려 자유롭게 움직입니다.

## 수정

**(1) 연직 제한** — `MosaicConfig.max_offnadir_ratio` (기본 0.35).
프레임의 바깥 고리를 아예 쓰지 않습니다. 내부는 중복 덕에 손실이 없고
(유효 중복 12.8 → 6.8배), 가장자리 밴드에서만 기복변위가 27% 줄어듭니다.
제한 때문에 아무도 못 덮는 픽셀은 `offnadir_fallback` 이 제한을 풀어 채우고,
그 비율을 `summary.json["ortho"]["offnadir_fallback_ratio"]` 에 남깁니다.

**(2) 관측수 기반 RTK 가중** — tie point 가 적은 프레임의 prior 가중치를
비례해서 올립니다 (상한 `--rtk-boost`, 기본 8배). 영상 제약이 약하면 RTK 를
더 믿는 것이 옳습니다. 완전히 고정하지는 않습니다 — 그러면 BA 가 그 프레임의
자세오차를 못 고칩니다.

**(3) 진단 추가** — `summary.json` 에 `observations_per_frame`
(중앙값 / 최소 / p10 / tie point 0인 프레임 수 / 총 점수) 이 들어갑니다.
로그에도 관측이 적은 프레임 수와 tie point 0 프레임 경고가 찍힙니다.

## 검증과 한계 — 솔직히 말씀드릴 것

* 타일 독립성은 연직 제한을 켠 뒤에도 유지됩니다 (**최대차 0, 불일치 0.0000%**).
* **연직 제한의 개선 효과는 합성으로 검증하지 못했습니다.** 제 합성 세트는
  24장이라 중복이 낮아, 제한을 걸면 예외 적용률이 54~59% 로 치솟습니다.
  실데이터는 380장·중복 12.8배라 예외율이 훨씬 낮게 나와야 정상입니다.
  **다음 실행의 `offnadir_fallback_ratio` 를 꼭 확인해 주세요** — 이 값이
  10% 를 넘으면 제한이 과하다는 뜻이니 `--max-offnadir 0.42` 정도로 완화하세요.
* 위 표의 기복변위는 기하 계산이지 실측이 아닙니다. 실제 개선폭은 바깥 영역
  어긋남을 다시 재봐야 압니다 (같은 194블록 측정을 다시 돌리면 비교됩니다).

## 확인 부탁드릴 것

이번 `summary.json` 의 `ground_plane` 값이 이전 실행과 소수점 이하까지
같습니다 (`n_inliers` 147, `inlier_rmse` 0.5668, `slope` 0.8302). 2단계 BA 가
실제로 동작했다면 점군이 크게 늘어야 하므로 이 값들도 달라져야 합니다.
`ba_reprojection_rmse_px` 는 0.58 → 1.25 로 바뀌었으니 무언가는 달라졌습니다만,
**로그의 다음 두 줄을 보내주시면 확실해집니다**:

```
[stage] triangulation 1차(느슨) (게이트 ... px): 점 N개, 관측 M개
  누적 자세 변화: 중앙값 X.XXX°, 최대 ...
```

1차 점 개수가 여전히 수백 개 수준이라면 병목은 삼각측량이 아니라 그 앞의

# 후속 2: 2단계 BA 는 성공, 그런데 기준면이 이득을 까먹고 있었다

## 좋은 소식 — 2단계 BA 가 확실히 동작했습니다

| | 이전 | 이번 |
|---|---|---|
| BA 총 점 수 | 147 | **231,713** (1576배) |
| 프레임당 관측 중앙값 | — | 1,832 |
| tie point 0인 프레임 | — | 1장 / 380 |

진단이 맞았고 수정이 통했습니다.

## 나쁜 소식 — 기준면이 8.2 m 아래로 밀렸습니다

`ground_plane.c` 가 113.67 → **105.45 m**. LRF 지면이 약 111.8 m 이므로
**지면보다 6.35 m 아래**입니다. GSD 도 0.00676 → 0.00806 으로 커졌습니다
(카메라–평면 거리 54.5 m, 실제 비행고도는 44.9 m).

범인은 `auto_plane`(겹침 시차 보정) 입니다. 이전 상한이
`max(0.2 × 카메라높이, 3.0)` = 8.9 m 였고, 보정량 −8.2 m 가 그 안에 들어와
통과했습니다.

이게 왜 치명적이냐면:

| 층 | 기준면 대비 Δh | 시임 단차(k≈0.10) | k=0.35 에서 |
|---|---|---|---|
| 지면 | 6.35 m | 1.27 m | 2.22 m |
| **패널 상면** | **8.75 m** | **1.75 m** | 3.06 m |

검사 대상인 패널이 기준면보다 8.75 m 위에 떠 있습니다. **BA 를 고쳐 얻은
이득을 기준면 오류가 그대로 까먹고 있었습니다.** 해상도도 21% 손해입니다.

(측정 주의: 이전 회차에서 제가 `mosaic_4` 의 리사이즈 배율을 빼먹어 어긋남을
1.98배 과소평가했습니다. 보정하면 mosaic_4 안쪽은 0.121 m 였습니다.)

## 수정

1. **`plane_calib` 상한을 절대값으로** — `max(0.2·h, 3.0)` → `max_shift_m`
   (기본 3.0 m). 누적 이동도 `total_limit_m` 로 묶습니다. 기준면은 지면과

# 후속 4: DSM 은 옳은 방향이었지만, 그 아래 더 근본적인 오류가 있었습니다

|---|---|---|

**BA 점군의 Z 가 통째로 틀렸습니다.** 그 점군으로 만든 DSM 이 픽셀마다
엉뚱한 높이를 주니 단일 평면보다 나빠진 것이 맞습니다.

## 진짜 원인: `f_px` 가 약 21% 큽니다

카메라 Z 를 역산하면 159.81 m, 점군 중앙 Z 가 105.60 m 이므로
**카메라–점군 거리 = 54.22 m** 입니다. 그런데 메타데이터는:

* `RelativeAltitude` ≈ 44.9 m (기압/GNSS)
* `LRFTargetDistance` ≈ 44~45 m (레이저)

**서로 독립인 두 센서가 일치**하는데 영상기하만 54.2 m 라고 합니다.
비율 **1.207**.

`compute_focal_px` 는 `FocalLengthIn35mmFilm / 36 × width` = 47/36×5184 =
6768 을 씁니다. H20T 줌 카메라의 35mm 환산 초점거리는 31.7~556.2 mm 범위라
EXIF 값이 실제 광학 상태와 어긋날 수 있습니다.

### 왜 BA 가 이걸 못 잡았나 — 초점거리–깊이 축퇴

점 위치가 자유변수이므로, f 가 21% 커도 BA 는 **점을 21% 깊게 밀어 넣어**
재투영을 완벽히 맞춥니다. RMSE 1.25 px 는 그래서 좋게 나온 것이지 3D 가
맞다는 뜻이 아닙니다. **RTK 로 카메라 위치를 고정해도 이 축퇴는 안 깨집니다**
— 위치는 맞고 깊이만 스케일되기 때문입니다.

합성으로 그대로 재현했습니다:

| | 점군 Z 중앙 | 카메라–점군 | RMSE |
|---|---|---|---|
| 진짜 f_px 5605 | 115.60 | 42.70 m | 0.39 px |
| 틀린 f_px 6768 | 106.72 | 51.58 m | 0.40 px |

거리 비율 1.208 = f 비율. RMSE 는 구분하지 못합니다.

이것이 그동안의 여러 증상을 한꺼번에 설명합니다 — 평면이 자꾸 8 m 아래로
내려간 것, `plane_calib` 이 −8.2 m 를 요구한 것, 평면 RANSAC inlier 가
147 개뿐이던 것 모두 같은 뿌리입니다.

## 수정: 초점거리 자기보정 (`homography/focal.py`)

축퇴를 깨는 것은 **독립적인 거리 관측**입니다. 기압고도계와 레이저가 바로
그것이고, 둘이 일치하면 그 비율이 곧 f 의 오차 배율입니다.

```
scale = (카메라–점군 거리) / (메타데이터 거리)
f_px_corrected = f_px / scale
```

1차 BA 뒤 한 번 계산해 적용하고, 보정된 f 로 삼각측량+BA 를 다시 돌립니다.

**검증** (진짜 f_px 5605, 틀린 값 6768 주입):

| 반복 | f_px | 점군 Z 중앙 (진짜 114.60) |
|---|---|---|
| 0 | 6768.0 | 106.72 |
| 1 | **5701.3** | **114.86** |

한 번에 수렴하고 f 오차는 +1.7% 로 줄었습니다.

안전장치: LRF 와 RelativeAltitude 가 서로 25% 이상 다르면 보정하지 않고,
배율이 [0.6, 1.6] 밖이거나 프레임별 산포가 ±0.08 을 넘으면 건너뜁니다.

## 함께 넣은 DSM 가드

DSM 기복이 `--dsm-max-relief`(기본 6 m)를 넘으면 **점군 품질 이상으로 보고
DSM 을 쓰지 않고 단일 평면으로 되돌립니다.** 이번 같은 24 m 짜리 DSM 이
모자이크를 망가뜨리는 일이 다시 없도록.

그 순환 실패를 초점 보정 직후에 다시 만든 것입니다.**

## 개선 사항 (3가지)

### 1. 초점 보정 후 느슨한 단계를 다시 실행

보정된 f 로 **느슨한 게이트 단계를 한 번 더** 돌려 카메라/점을 새 f 에 맞춘
뒤에 정밀 단계로 갑니다. 단계 목록에 동적으로 삽입하는 방식이라 초점 보정이
여러 번 일어나도 매번 재실행됩니다 (`--focal-rounds`, 기본 2회 상한).

이것으로 점군이 다시 20만 개대로 돌아와야 하고, 그러면 DSM 도 켜집니다.

### 2. 연직 제한 자동 조정

`max_offnadir_ratio` 는 프레임 최대 off-nadir 에 상대적인 의미를 갖는데,
**초점거리가 보정되면 그 최대값이 변합니다** — 이번에 k_max 가 0.479 →
0.552 로 커지면서 같은 0.35 제한의 예외율이 7.7% → **13.4%** 로 뛰었습니다.

각 픽셀을 덮는 프레임들의 **최소 k** 분포에서 목표 예외율 분위수를 잡아
제한값을 자동 결정합니다. 초점거리나 중복도가 달라져도 예외율이 일정하게
유지됩니다. 검증에서 목표 5% 에 대해 실제 4.6% 가 나왔습니다.
(`--no-offnadir-auto`, `--offnadir-target`)

### 3. DSM 기각 사유를 기록

지금은 `dsm_used: false` 만 있고 왜 꺼졌는지 알 수 없었습니다.
`summary.json` 에 `dsm_rejected` 로 사유(`relief_too_large` /
`too_few_points` / `build_failed_see_log`)와 관련 수치를 남깁니다.

## 다음 실행에서 볼 것

```

  보정된 f 로 느슨한 단계를 다시 실행합니다 (게이트 ... px)
[stage] triangulation 1차-재실행#1(느슨): 점 N개, 관측 M개
연직 제한 자동 결정: k ≤ 0.xxx (프레임 최대 0.55x, 목표 예외율 5%)
DSM 생성: ... 기복 X.XX m
```

* 재실행 단계의 **점 개수가 20만 개대**로 회복돼야 합니다. 그러면 부작용이
  해소된 것입니다.
* 2회차 배율이 **1.00 근처**로 나와야 수렴한 것입니다.
* 그 뒤 **DSM 기복이 2~3 m** 로 나오면 비로소 2층 구조가 제대로 처리됩니다.

### 초점거리 — 2회차까지 수렴 진행

## 역효과가 난 것

### 1. 연직 제한 자동 조정이 제한을 무력화했습니다

```
자동 결정 k ≤ 0.5641,  프레임 최대 k = 0.5641   →  제한 없음
예외율 13.4% → 0.0%,  충전율 0.864 → 0.800
```

**목표를 잘못 잡았습니다.** "예외율이 5% 가 되도록" 분위수로 정했는데,
모자이크 가장자리 밴드가 전체의 5% 를 넘으므로 95 분위수가 곧 프레임
최대값이 됩니다. 예외 픽셀은 "더 나은 선택지가 아예 없는 자리" 라 많아도
손해가 아닌데, 그걸 최소화하려다 정작 중요한 것(선택지가 있는 자리에서
연직에 가까운 쪽 쓰기)을 잃었습니다.

**수정**: 규칙을 단순화했습니다 — 제한값 = 프레임 최대 k × `offnadir_frac`
(기본 0.65). H20T 기준 k ≈ 0.37 로 원래 의도했던 0.35 와 비슷하고,
초점거리가 보정돼 k_max 가 변해도 (0.479 → 0.564) 비율이 유지되므로 자동으로
따라갑니다. (`--offnadir-frac`)

### 2. DSM 이 또 기각됐습니다 — 다만 원인은 다릅니다

```
dsm_rejected: relief_too_large, 기복 35.3 m, 충전율 25.8%
```

초점이 거의 맞았는데도 점군 Z 가 35 m 에 걸쳐 흩어져 있습니다. 원인 두 가지:

**(a) 셀이 너무 작습니다.** 0.4 m 셀은 이 점 밀도에서 **셀당 1 점 이하**입니다.
중앙값·MAD 이상치 제거가 성립할 수 없고, 채워진 셀은 이상치 하나가 그대로
높이가 됩니다. 충전율 25.8% 가 그 증거입니다.

**(b) 반복 텍스처 오매칭.** 패널 셀 주기 0.23 m 에서 한 칸 어긋난 매칭은
**재투영이 완벽한데 깊이만 6.5 m 틀립니다.** 3 px 게이트로는 절대 안 걸러
집니다. 셀 단위 MAD 로도 부족합니다 — 한 셀이 통째로 이상치일 수 있습니다.

**수정**: `dsm.py` 가 (a) 점 밀도에서 셀 크기 자동 결정 (b) 전역 로버스트
평면 기준 ±4 m 밴드로 **격자에 넣기 전에** 점을 정제하도록 되어 있는데,
파이프라인이 기준 평면을 넘기지 않아 그 경로가 꺼져 있었습니다. 이제
`plane=plane` 을 전달합니다.

검증 (실측과 같은 36 m 산포 점군, 이상치 45%):

| | 기복 | 충전율 |
|---|---|---|
| 정제 전 | 36.2 m | — |
| 정제 후 (자동 셀 1.45 m) | **1.51 m** | **90.3%** |

# 후속 7: 로그 분석 — 초점은 수렴, 그러나 BA 가 달아나고 있었습니다

로그를 주신 덕분에 그동안 summary.json 만으로는 볼 수 없던 것이 드러났습니다.

## 성공: 초점거리 수렴

| 회차 | 배율 | f_px |
|---|---|---|
| 1 | 1.1530 | 5869.9 |
| 2 | 1.0220 | 5743.5 |
| 3 | **1.0040** | (허용오차 내 → 적용 안 함) |

삼각측량 거리 52.30 → 46.45 → **45.65 m**, 메타데이터 45.33 m 대비 잔차
**+0.7%**. 초점거리 문제는 끝났습니다.

## 심각: BA 가 발산하고 있습니다

```
누적 자세 변화: 중앙값 10.728°, 최대 20.758°
RTK prior 대비 카메라 이동: 중앙값 1.823 m, 최대 8.529 m
```

* BA 시작 전 재투영 RMSE 110.7 px = 자세오차 **0.94°**. 고쳐야 할 양은
  1° 미만인데 **10.7° 를 움직였습니다.** 고친 것이 아니라 달아난 것입니다.
* RTK σ_xy 는 **1.1 cm** 입니다. 1.823 m 이동은 **166σ** — 물리적으로
  불가능합니다.

원인은 구조적입니다:

```
영상 잔차 1,799,056개  vs  RTK 잔차 1,140개   (1578 : 1)
자세에는 prior 가 아예 없음
```

RTK prior 가 수적으로 무력하고, 짐벌이 ±1~2° 정확한데도 BA 가 20° 를 돌릴
수 있는 구조였습니다. 연쇄 피해도 로그에 그대로 있습니다:

* 복원점 Z 범위 **−52.7 ~ 346.4 m** (지면 113.4 m)
* 평면 RANSAC inlier 23.7% → 실패 → LRF 폴백
* DSM 셀 1.75 m 로도 충전율 16.8% → 폐기
* BA 1단계가 매번 `nfev=300` 상한에 걸림 (88분 중 **62분**이 BA)

## 수정

### 1. 카메라 위치를 RTK 에 고정 (기본)

RTK Fixed 의 1.1 cm 는 BA 가 영상만으로 도달할 수 있는 정확도보다 훨씬
좋습니다. **추정할 이유가 없습니다.** 위치를 파라미터에서 빼면 RTK 잔차 자체가
사라져 가중치 균형 문제가 없어지고, 블록의 평행이동·축척 자유도가 원천 제거
됩니다.

### 2. 자세 prior (σ = 2°)

짐벌 절대 정확도 수준의 벌점을 줍니다. 관측이 적은 가장자리 프레임(로그상
85장)이 소수의 오매칭에 끌려가는 것을 막습니다.

### 3. 삼각측량 Z 밴드 필터 (지면 ±25 m)

느슨한 게이트가 통과시킨 −52~346 m 짜리 점을 BA 에 넣기 전에 제거합니다.

**검증** (카메라 150, 점 12,000, 관측 192,815, 오매칭 15%):

| | 시간 | 자세오차 | 위치 이동 | RMSE |
|---|---|---|---|---|
| 기존 | 39.9 s | 0.093° | 0.061 m | 16.5 px |
| 신규 | **6.2 s** | **0.054°** | **0.000 m** | 16.6 px |

**6.5배 빠르고 자세도 더 정확합니다.** 위치 이동은 정의상 0 입니다.

솔직히 말씀드리면, 제 합성으로는 실데이터의 10.7° 발산을 **재현하지
못했습니다** (여러 조건을 시도했습니다 — 2장짜리 track 60%, 오매칭 15%,
틀린 f). 원인 메커니즘을 완전히는 특정하지 못했습니다. 다만 위치 고정과 자세
prior 는 그 두 증상을 **구조적으로 불가능하게** 만드는 것이지 튜닝이 아니므로,
메커니즘을 몰라도 안전한 수정입니다.

### 4. `plane_source` 라벨 버그

로그에는 "BA 점군 평면 적합 실패 — LRF/메타데이터로 폴백" 이 찍혔는데
summary 에는 `"ba_points"` 로 기록됐습니다. `n_inliers: 147` 이 네 번의 실행
내내 같았던 것도 이것으로 설명됩니다 — **147 은 BA 점군이 아니라 LRF 380점의
적합 결과**였습니다. 이제 `"lrf_fallback"` 으로 구분해 기록합니다.

## 다음 실행에서 볼 것

```
BA(RTK고정): 카메라 380(자세만), ... | 시작 재투영 RMSE 110.7 px
BA 완료. ... | 자세 변화 중앙값 1.xx°, 최대 x.xx° | 카메라 위치 RTK 고정
  Z 밴드 필터: N개 제거
```

* **자세 변화가 2° 이내**여야 정상입니다 (초기 오차 0.94° + prior σ 2°).
  이전의 10.7° 가 여기서 잡히면 그 아래 문제들이 연쇄적으로 풀립니다.
* 복원점 Z 범위가 **100~130 m** 안에 들어와야 합니다.
* 평면 RANSAC inlier 비율이 30% 를 넘어 `plane_source: "ba_points"` 가
  되는지 — 이번엔 라벨이 정확합니다.
* 그 다음에야 DSM 이 켜질 수 있습니다.
* 실행 시간도 88분에서 크게 줄어야 합니다 (BA 가 62분이었으므로).

## 되돌리는 법

위치를 정말 풀어야 한다면 `--free-positions` 입니다. 다만 그때는 로그의
"카메라 이동" 을 반드시 확인하세요 — 1.1 cm σ 대비 몇 σ 인지가 판단 기준입니다.

# 후속 8: BA 수정이 통했습니다 — 남은 것은 '블록 기울기'

## 확실히 좋아진 것

| | 이전 | 이번 |
|---|---|---|
| 평면 출처 | LRF 폴백 (라벨은 ba_points) | **진짜 BA 점군** |
| 평면 inlier | 147 (=LRF 380점 중) | **27,085** |
| 평면 적합 RMSE | 0.565 m | **0.291 m** |
| 충전율 | 0.801 | **0.913** (역대 최고) |

`n_inliers` 가 147 에 고정돼 있던 네 번의 실행이 끝났습니다. BA 점군이
평면 RANSAC 을 통과할 만큼 깨끗해졌다는 뜻이고, 위치 고정 + 자세 prior 가
의도대로 동작했습니다.

## 남은 문제 1: 블록이 남북으로 기울었습니다

| | a | b | 기울기 | 사이트 양끝 표고차 |
|---|---|---|---|---|
| BA 점군 | +0.00857 | **−0.04295** | **2.508°** | 6.75 m |
| LRF 380점 | +0.01017 | **+0.01049** | 0.837° | 2.25 m |

**a 는 비슷한데 b(남북) 만 부호가 뒤집히고 4배가 됐습니다.** 우연이 아닙니다:

* 비행선이 **동서**(gimbal yaw ±90°) 입니다.
* 그 배치에서 **피치 편향은 영상만으로 관측되지 않습니다** — 근평면 장면의
  게이지 자유도입니다.
* 피치 편향은 정확히 **남북 기울기**로 나타납니다. b 가 튄 방향과 일치합니다.

자세 prior σ=2° 는 블록 전체가 함께 도는 것을 막기엔 느슨했습니다
(σ=2° → 사이트 양끝 5.4 m 까지 허용).

### 수정: LRF 로 기울기 교차검증

LRF 는 380개 지점의 **레이저 실측**이고 영상 기하와 **완전히 독립**입니다.
자세 편향의 영향을 받지 않으므로 이 자유도를 판정할 수 있습니다.

BA 평면과 LRF 평면의 기울기 차이가 `--plane-tilt-tol`(기본 1°)를 넘으면
**LRF 기울기를 채택하고 높이는 BA 것을 유지**합니다.

검증:

```
BA 기울기 2.508° → 채택 후 0.837°   (중심 높이 114.2278 → 114.2278 m, 완전 보존)
사이트 양끝(±77 m N) 표고: 110.92/117.53  →  115.04/113.42
```

자세 prior 도 σ 2.0° → **1.0°** 로 조였습니다 (짐벌 절대 정확도 수준).

## 남은 문제 2: 초점거리가 진동합니다

| 실행 | 배율 | f_px |
|---|---|---|
| 이전 (BA 발산 상태) | 1.1530 → 1.0220 → 1.0040 | **5743.5** |
| 이번 (BA 정상) | 0.9647 | **7015.7** |

**두 실행이 반대 방향으로 22% 어긋났습니다.** 이전 값은 발산한 점군에서
나온 것이라 신뢰할 수 없지만, 이번 값도 1회로 멈췄고 최종 잔차가 **−2.6%**
남았습니다 (GSD×f = 44.16 m vs 메타 45.33 m).

### 수정 3가지

1. **감쇠** — 한 번에 전량 보정하지 않고 70% 만 적용한 뒤 다음 라운드에서
   재측정합니다. 진동을 막습니다.
2. **누적 클램프** — EXIF 대비 ±25% (`--focal-max-total`) 를 넘는 누적 보정은
   중단합니다.
3. **최종 검증** — 모든 단계가 끝난 뒤 `GSD × f_px` 를 메타데이터 거리와
   비교해 로그와 `summary.json["focal_calibration"]["final_check"]` 에
   남깁니다. 잔차 3% 초과면 경고합니다.

반복 상한도 3 → 4 회로 올렸습니다.

## 다음 실행에서 볼 것

```
블록 기울기 교차검증: BA 2.5xx° vs LRF 0.8xx° — LRF 기울기를 채택합니다
초점거리 최종 검증: GSD×f_px = 45.xx m vs 메타데이터 45.33 m → 잔차 ±x.x%
```

* **기울기 교차검증 경고가 뜨면** 그 자유도가 실제로 틀어져 있었다는

    r      0~   540 px : 중앙값   x.xx px
    ...
    r   2700~  3240 px : 중앙값   x.xx px
    → 최대/최소 비 x.x배,  r³ 적합 R²=x.xx,  함의 k1=±x.xxxxx
```

* **최대/최소 비가 3배 이상이고 R² > 0.8** 이면 왜곡이 맞습니다 →
  `--estimate-distortion` 을 추가해 한 번 더 돌려 주세요. 그러면 정밀 단계
  생존 점이 133,011 에서 크게 늘어야 합니다.
* **비가 1.8배 미만**이면 왜곡이 아니라 오매칭/자세오차입니다 → 그때는
  매칭 단계(2장짜리 track 55%)를 손봐야 하고, 왜곡 보정은 켜지 마세요.

이 한 줄이 그동안 추측으로 오갔던 문제를 확정해 줄 것입니다.

# 후속 12: 진단이 답을 줬습니다 — 그리고 제 적합식에 버그가 있었습니다

## 진단 결과 (중간 단계, RMSE 5.21 px)

```
r      0~  477 px : 1.47 px      r  1430~ 1906 px : 2.83 px
r    477~  953 px : 1.74 px      r  1906~ 2383 px : 3.74 px
r    953~ 1430 px : 2.38 px      r  2383~ 2859 px : 5.59 px
→ (로그) 최대/최소 3.8배, r³ 적합 R²=0.14, 함의 k1=+0.01728
```

**잔차가 반경에 따라 분명히 자랍니다.** 그런데 제 진단이 "R²=0.14" 라고
잘못 보고했습니다.

### 제 버그: 절편을 빼먹었습니다

잔차는 **'오매칭·잡음이 만드는 반경 무관 바닥' + '반경에 따라 자라는 성분'**
의 합인데, 절편 없이 r³ 만 맞추려 하니 바닥까지 r³ 로 설명하려다 적합이
무너졌습니다.

| 적합 | 결과 |
|---|---|
| 절편 없음 (제 버그) | R² = **0.14** → "왜곡 아님" 오판 |
| **절편 포함** | **바닥 1.72 px + 반경성분 3.87 px, R² = 0.985** |

수정했고, 구간도 6 → 10 개로 늘려 다음 실행에서 멱수를 더 잘 가릅니다.

## 확정된 것과 확정 못한 것

**확정**: 잔차는 바닥 1.72 px 위에 반경에 따라 자라는 3.87 px 가 얹혀 있습니다
(R²=0.985).

**확정 못함**: 그 성분이 렌즈 왜곡(r³)인지 다른 것(r²)인지.
6개 구간으로는 `r² (R²=0.982)` 와 `r³ (R²=0.985)` 이 구분되지 않습니다.
그리고 제 합성에서는 **BA 가 왜곡을 흡수해 버려** 이 현상을 두 번 다
재현하지 못했습니다. 원인을 단정할 근거가 없습니다.

## 그래서 원인에 의존하지 않는 수정을 했습니다

원인이 무엇이든 **확정된 사실**이 하나 있습니다:

```
정밀 게이트가 상수 3 px 이라 반경 1814 px 바깥이 통째로 잘린다
= 프레임 반경의 56% 지점.  점 손실 50% 와 정확히 일치.
```

상수 게이트는 **이미지 중심 쪽 점만 남겨 점군을 편향**시킵니다. 게이트를
측정된 프로파일(바닥 + 반경성분)에 맞추면 반경 전체에서 고르게 남습니다.

```
정밀 게이트를 측정 프로파일로 조정: 3.0 → 5.6 px (바닥 1.72 + 반경성분 3.87)
```

| 게이트 | 통과 반경 | 프레임 반경 대비 |
|---|---|---|
| 3.0 px (현재) | 1,814 px | 56% |
| **5.6 px (자동)** | **2,624 px** | **81%** |
| 8.0 px (상한) | 3,080 px | 95% |

**점 133,011 → 25만 안팎 회복**을 기대합니다. 상한 8 px 를 둔 것은 그 이상
열면 진짜 오매칭이 들어오기 때문입니다. (`--fixed-fine-gate` 로 끄기,
`--fine-gate-max` 로 상한 조절)

## 왜곡 보정은 여전히 opt-in 입니다

한 번 `auto` 로 바꿨다가 되돌렸습니다. 제 합성에서 효과를 입증하지 못했고
멱수도 확정 못 한 상태에서 기본값을 바꾸는 것은, 앞서 DSM 을 검증 없이

원하시면 `--estimate-distortion` 으로 한 번 시험해 보실 수 있습니다.
게이트 자동 조정과 함께 쓰면 어느 쪽이 기여했는지 섞이므로, 비교하시려면
따로 돌리시는 편이 낫습니다.

## 바로잡은 것 1: 왜곡 추정이 병적인 해를 냈습니다

로그에 **경고가 찍혔는데도 적용**됐습니다:

```

  왜곡 모델로 설명되는 부분이 적습니다 (1.87 → 1.78 px)   ← 5% 만 설명

두 계수의 기여를 뜯어보면 병적입니다:

| 반경 | k1 항 | k2 항 | 합 |
|---|---|---|---|
| 1000 px | −0.54 | +0.12 | −0.42 |
| 2000 px | −4.33 | +3.95 | −0.38 |
| 2859 px | −12.64 | **+23.57** | +10.92 |
| 3240 px | −18.40 | **+44.05** | **+25.65** |

중간 반경에서 서로 상쇄하다가 모서리에서 k2 가 폭주합니다. k1 과 k2 는
강하게 상관돼 있어 함께 풀면 이런 해가 나옵니다 (ill-conditioned).

**수정 3가지:**

1. **k1 단독**이 기본입니다 (`--distortion-k2` 로 2항 사용).
2. **절편(반경 무관 바닥)을 함께 적합**합니다 — 바닥을 왜곡으로 오해하지
   않도록.
3. **설명률 25% 미만이면 기각**합니다. 경고만 하고 적용하던 것을 실제로
   막습니다.

검증:

| 케이스 | 결과 |
|---|---|
| 진짜 k1=−0.0107, 바닥 1.2 px | **k1=−0.01067 복원**, 설명률 46% → 적용 |
| 왜곡 없음, 바닥 2.5 px | 설명률 −0% → **기각** |

(`--no-auto-distortion` 으로 끄기)

## 이번 수정: 조기 종료가 과했습니다

```

재실행#1(느슨)  : 1단계 nfev= 9  → 자세 변화 0.001°  ← 아무 일도 안 함
왜곡보정 후(느슨): 1단계 nfev=12 → 자세 변화 0.001°  ← 아무 일도 안 함

```

`ftol=1e-3` 이 너무 느슨해 1단계가 즉시 멈췄고, 2단계에는 tol 을 걸지
않아 거기서 시간을 다 썼습니다. 부수 효과로 초점 반복도 2회 → 1회로
줄었습니다 (느슨한 BA 가 일을 안 하니 2회차가 이미 허용오차 안).

**수정**: 기본값 `1e-3 → 1e-4` 로 조이고 **두 하위 단계 모두**에 적용합니다.
검증 (카메라 120, 관측 232,278):

| ftol | 시간 | 자세오차 | 정밀 생존 점 |
|---|---|---|---|
| 없음 | 12.9 s | 0.129° | 6,672 |
| 1e-3 | 5.2 s | 0.129° | 6,670 |
| **1e-4** | **6.5 s** | **0.129°** | **6,670** |
| 1e-5 | 7.3 s | 0.129° | 6,670 |

품질은 모두 동일하고 1e-4 가 2배 빠릅니다.
